# Inventory and supply request operations

The RPCs in the transactional migration identify the actor from Supabase Auth and require an active profile and active facility. Do not trust client-supplied user IDs or grant direct table writes.

## MVP rules

- Facility administrators and inventory managers can create batches, edit batch metadata and adjust stock at their own facility. Initial quantities and adjustments create stock movements. An adjustment cannot consume reserved stock. Metadata changes are separately audited; expiry cannot change while stock is reserved.
- The `create_inventory_batch_with_medicine` RPC atomically adds or selects a shared catalogue entry by all formulation fields (name, generic name, optional brand, active ingredient, strength, dosage form and unit) and creates the initial batch. Only a single exact normalized match is reused; ambiguous catalogue duplicates fail closed. Catalogue additions require generic name and active ingredient and never infer clinical interchangeability. Direct table writes remain disabled.
- Facility administrators and requesting staff can create outgoing requests for an active supplier and catalogue medicine. Approval, not creation, confirms whether enough eligible stock is available.
- Facility administrators and supplier staff can approve or reject pending incoming requests. Approval allocates the entire requested quantity across non-expired batches in expiry/date ID order. Batch locks and the request status change run in the same transaction. Partial approvals are not supported.
- Requesting staff or authorised supplier staff may cancel a pending or approved request for their own facility. Cancellation releases the reservation; terminal requests cannot be cancelled.
- Authorised supplier staff can fulfil an approved request once, after uploading a proof photo to the private `request-proof-photos` bucket. The object path must be `<request-uuid>/<file-uuid>.(jpg|png|webp)` with lowercase canonical UUIDs. The bucket limits uploads to 5 MiB and JPEG, PNG or WebP MIME types. `fulfil_supply_request_with_proof(p_request_id, p_object_path)` verifies the private uploaded object, request binding, reservations and expiry, then atomically deducts supplier stock, records the proof and events, and marks the request `FULFILLED`. Missing, mismatched or repeated proof/fulfilment attempts fail without committing changes. The legacy `fulfil_supply_request(p_request_id)` remains callable for compatibility but fails closed because it cannot provide a photo path.
- Only active users at either active facility on the request can read proof metadata or private photo objects. Only authorised supplier administrators/staff can upload for their own approved incoming requests. They can delete an uploaded object only while it is unregistered; a registered proof is not client-deletable. An abandoned object can remain if its request is no longer approved, and may require trusted storage administration to clean up.
- The requesting facility administrator or requesting staff can call `confirm_supply_request_receipt_with_inventory(p_request_id, p_batches)` once after fulfilment. `p_batches` is a nonempty JSON array of `{batch_number, quantity, expiry_date}` lines. The positive quantities must sum exactly to `fulfilled_quantity`; partial, excess or otherwise mismatched counts fail closed, leave the request `FULFILLED`, and make no inventory, movement or receipt changes. This MVP does not record a discrepancy or partial intake; resolve the mismatch operationally before retrying. Each distinct received batch/expiry is kept as its own receiving inventory batch, while an existing batch number is incremented only when its expiry matches. The RPC atomically inserts receipt lines and `RECEIPT_IN` movements, updates inventory, marks the request `RECEIVED` and records the actor/time/event. The old `confirm_supply_request_receipt(p_request_id)` signature remains callable but always fails closed for new confirmations; already-`RECEIVED` rows are not backfilled.
- Reserving or releasing stock does not refresh the physical inventory timestamp. All stock remains reported availability and requires confirmation.

## RPC signatures

- `create_inventory_batch(p_facility_id, p_medicine_id, p_batch_number, p_quantity, p_expiry_date, p_low_stock_threshold)`
- `create_inventory_batch_with_medicine(p_facility_id, p_medicine_name, p_generic_name, p_brand_name, p_active_ingredient, p_strength, p_dosage_form, p_unit_of_measure, p_batch_number, p_quantity, p_expiry_date, p_low_stock_threshold)`
- `adjust_inventory(p_batch_id, p_delta, p_notes)`
- `update_inventory_batch(p_batch_id, p_batch_number, p_expiry_date, p_low_stock_threshold, p_notes)`
- `find_medicine_matches(p_requesting_facility_id, p_medicine_id, p_requested_quantity)` returns full matches, separately listed insufficient stock and effective scoring settings.
- `create_supply_request(p_requesting_facility_id, p_supplying_facility_id, p_medicine_id, p_quantity, p_notes)`
- `approve_supply_request(p_request_id)`
- `reject_supply_request(p_request_id, p_notes)`
- `cancel_supply_request(p_request_id, p_notes)`
- `fulfil_supply_request_with_proof(p_request_id, p_object_path)`
- `fulfil_supply_request(p_request_id)` (compatibility signature; fails closed without a proof path)
- `confirm_supply_request_receipt_with_inventory(p_request_id uuid, p_batches jsonb)` (array of objects with exactly `batch_number` (string), `quantity` (positive integer) and `expiry_date` (`YYYY-MM-DD`); the sum must equal `fulfilled_quantity` and batch numbers must be unique within the call)
- `confirm_supply_request_receipt(p_request_id uuid)` (legacy; fails closed without batch details)

Mutation functions return the affected batch or request UUID; the matching function returns a JSON result. PostgreSQL rejects invalid input, unauthorised actions, insufficient stock and invalid status transitions. Integration tests against a real Supabase instance, including simultaneous approvals, remain required before relying on this design.

## Local tests

`tests/inventory_metadata.cjs` checks metadata authorization, isolation and audit. `tests/inventory_medicine_catalogue_entry.cjs` checks role/facility authorization, exact formulation reuse, duplicate handling, rollback and initial stock audit. `tests/operations.cjs` exercises the workflow with PGlite and a Supabase Auth stub. `tests/photo_proof_receipt.cjs` applies the initial schema, transactional operations and photo/receipt migrations locally, seeds isolated fictional facilities, and stubs Supabase Auth and Storage tables. `tests/receiving_inventory.cjs` applies the receipt-intake migration and checks exact multi-batch reconciliation, atomic rollback on quantity or expiry mismatch, role/facility isolation, batch-level stock movements, RLS, and replay/uniqueness protection. Demo-account, inventory and coordinate seed migrations are intentionally omitted. The isolated PGlite receipt test does not exercise true parallel transactions; request-row locking and unique constraints provide replay/race protection, but concurrent receipt integration testing against PostgreSQL remains open. `tests/concurrency.cjs` uses two independent connections to an isolated PostgreSQL 17 server and verifies that competing approvals cannot allocate the same stock and concurrent duplicate fulfilment deducts stock only once. The temporary server is stopped after the test.

Install `@electric-sql/pglite`, `pg` and `embedded-postgres@17.11.0-beta.19` in a separate test environment and make them available on `NODE_PATH`, then run the scripts from the repository root. Run the photo/receipt suite with `NODE_PATH="$HYPER_SCRATCH_DIR/node_modules" node supabase/tests/photo_proof_receipt.cjs`; run receipt intake checks with `node supabase/tests/receiving_inventory.cjs`. Both require only PGlite. These local tests passed, but they do not replace authenticated integration tests on Supabase.

## Medicine discovery and scoring

The matching RPC checks the caller's active facility and role, then aggregates only positive, unreserved, non-expired batches for the exact medicine at other active facilities. Facilities with insufficient eligible stock appear separately; no score can override eligibility. Full matches are ranked by quantity (50%), distance (30%) and freshness (20%) by default. Quantity is capped at 100, so all full matches have a quantity score of 100. Distance uses a straight-line estimate and declines to zero at 100 km; missing coordinates use a configurable fallback of 50/100 rather than an invented distance. Freshness uses the oldest update among eligible positive-availability batches and declines to zero over 168 hours. Data at least 168 hours old is flagged, not excluded. The singleton settings table is configurable through trusted database administration; clients cannot modify it. These are demo defaults, not validated operational parameters.

Matching does not reserve or guarantee stock and does not assess quality, clinical suitability, regulatory compliance or delivery. The demo coordinates in the demo_coordinates migration are invented for fictional facilities and must never be presented as real locations. The deployed demo currently has one supplier; local tests include multiple suppliers, insufficient stock, stale data, inactive facilities and expired batches.

Run `NODE_PATH="$HYPER_SCRATCH_DIR/node_modules" node supabase/tests/medicine_matching.cjs` for the local matching checks. Authenticated end-to-end comparisons across multiple real Supabase accounts remain outstanding.

## Facility profiles and manual verification

Facility administrators can submit their own public profile and private licence number, authority and expiry via `submit_facility_profile`. Every submission resets the profile to `UNVERIFIED`. Platform administrators can create, edit or deactivate profiles via `platform_admin_save_facility`; deactivation is blocked while pending or approved requests involve the facility. A change to name, type, address or coordinates resets verification. Licence information and its history are readable only to the facility's administrator and platform administrators; the public directory excludes those details.

Only platform administrators can approve or reject a submission using `review_facility_verification`, with a non-empty note documenting the manual record check. A verified decision requires a current unexpired licence. Reviews and profile changes are audited. `facility_directory` and matching responses mask expired verification as `UNVERIFIED`; a MediNexus review is not a regulator-issued accreditation. See `supabase/FACILITY_CONTRACT.md` for the complete API.

After installing `@electric-sql/pglite` in an isolated test environment, run `NODE_PATH="$HYPER_SCRATCH_DIR/node_modules" node supabase/tests/facility_verification.cjs`. The suite applies the foundation, transactional, matching, photo-proof and facility migrations locally with Auth and Storage stubs. It does not replace real authenticated Supabase integration tests. A platform administrator account must be provisioned separately; no self-registration or staff onboarding is provided.
