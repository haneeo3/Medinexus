# Facility profile and verification contract

This contract describes the database API introduced by the facility-management migration. Facility identity is derived from `auth.uid()` and `public.profiles`; callers cannot submit an actor ID. No direct client writes are granted.

## RPCs

- `submit_facility_profile(p_name text, p_facility_type text, p_address text, p_latitude double precision, p_longitude double precision, p_image_url text, p_license_number text, p_license_authority text, p_license_expiry_date date) returns table (facility_id uuid, verification_status text, updated_at timestamptz)`. A `FACILITY_ADMIN` may update only their own facility's public profile and private licensing details. It creates a private license record if needed. Any owner-submitted profile or license change (including a no-op resubmission) sets status to `UNVERIFIED`, clears the prior decision, and appends history. Licence fields are never included in public facility reads or general profile history.
- `platform_admin_save_facility(p_facility_id uuid, p_name text, p_facility_type text, p_address text, p_latitude double precision, p_longitude double precision, p_image_url text, p_operational_status text) returns uuid`. A `PLATFORM_ADMIN` creates a facility when `p_facility_id` is null, or edits the supplied facility. `p_operational_status` is `ACTIVE` or `INACTIVE`. Admin-created facilities begin `UNVERIFIED`. Changes to name, type, address, or coordinates reset verification to `UNVERIFIED`; image-only and operational-status changes preserve verification. Every change is recorded in history. Deactivation is blocked while this facility is on either side of any `PENDING` or `APPROVED` supply request.
- `review_facility_verification(p_facility_id uuid, p_decision text, p_notes text) returns uuid`. Only a `PLATFORM_ADMIN` may set `p_decision` to `VERIFIED` or `REJECTED`; each decision appends an immutable review event/history entry. A `VERIFIED` decision requires an existing current licence submission with `license_expiry_date >= current_date`; every decision requires a nonempty `p_notes` recording the manual record check/source or rejection reason. A submitter cannot review their own submission. Rejected submissions may lack a current licence. A facility must be `UNVERIFIED` before review. Facility admins cannot review, and direct writes to all facility and review tables are denied.

All three RPCs are `SECURITY DEFINER` with an empty `search_path`, revoke execution from `PUBLIC` and `anon`, and grant execution to `authenticated`. Inputs are validated in the database. Image URLs must be HTTPS with a hostname and no credentials embedded in the authority when present; coordinates must be both null or both in geographic bounds; facility type is `CLINIC`, `PHARMACY`, or `HOSPITAL` for this workflow.

## Read selects

The medicine discovery RPC `find_medicine_matches(p_requesting_facility_id uuid, p_medicine_id uuid, p_requested_quantity integer)` keeps its existing signature, result type, and security; its `matches[*].verification_status` and `insufficient[*].verification_status` use the same expiry-aware effective rule as `facility_directory`, so an expired stored VERIFIED facility is reported as UNVERIFIED. The RPC still returns no licence fields.

- Public directory (no licence columns): `select id, name, facility_type, address, latitude, longitude, image_url, verification_status, verification_valid_until, operational_status, created_at, updated_at from public.facility_directory where ...`. This security-invoker view preserves the `facilities` RLS boundary. Its `verification_status` is effective: VERIFIED only when the stored status is VERIFIED and `verification_valid_until >= current_date`; otherwise an expired VERIFIED row is returned as UNVERIFIED. The date field is also returned for explicit client presentation. Do not use `public.facilities.verification_status` directly for display; use this view or evaluate that exact rule.
- Private current licence: `select facility_id, license_number, license_authority, license_expiry_date, submitted_by, submitted_at, updated_at from public.facility_licenses where facility_id = ...`. RLS allows only an active `PLATFORM_ADMIN` or the active `FACILITY_ADMIN` assigned to that facility (facility operational status does not change the private-record boundary). Do not expose this table in discovery or other facility queries.
- Facility history: `select id, facility_id, actor_id, action, before_profile, after_profile, notes, created_at from public.facility_history where facility_id = ... order by created_at desc`. RLS allows only an active `PLATFORM_ADMIN` or the assigned active `FACILITY_ADMIN`. Snapshots contain public profile/status fields only, never licence values.
- Private licence versions: `select id, facility_id, actor_id, before_license, after_license, created_at from public.facility_license_history where facility_id = ... order by created_at desc`. Same restricted RLS as current licence data; values must never be joined into public discovery reads.
- Review log: `select id, facility_id, reviewer_id, decision, notes, created_at from public.facility_verification_reviews where facility_id = ... order by created_at desc`. Same restricted RLS as facility history; review notes are staff-only and are not returned by public facility selects.

## Result and status semantics

`submit_facility_profile` returns one row with the facility UUID, resulting status (always `UNVERIFIED`), and `updated_at`. The platform admin save and review RPCs return the affected facility UUID. `public.facilities.verification_status` is the stored state; `verification_valid_until date` is null unless verified and is set to the submitted licence expiry date on approval. The public directory returns effective `verification_status`, masking expired VERIFIED as UNVERIFIED. Clients displaying status must query `public.facility_directory` (or apply `verification_status = 'VERIFIED' AND verification_valid_until >= current_date`); never show a stored VERIFIED status after its validity date. Status values remain `UNVERIFIED`, `VERIFIED`, and `REJECTED`. Any owner resubmission transitions `VERIFIED` or `REJECTED` back to `UNVERIFIED`; only a platform-admin review can set `VERIFIED` or `REJECTED`. Every submission, profile edit, deactivation, and review is audited. Licence field versions are retained in `facility_license_history`, which has the same restricted RLS as the current licence table. No licensing data is stored in public snapshots or review logs. Name/type/address/coordinate changes by either owner or platform admin reset verification; image-only or operational-status-only platform edits preserve the current verification state. A VERIFIED decision is permitted only with a current unexpired submitted licence and a nonblank manual-check note. Rejecting an expired or absent licence is allowed with a nonblank reason. Direct table writes are revoked.
